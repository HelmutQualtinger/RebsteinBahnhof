# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A static, dependency-free web app (`index.html` + `style.css` + `app.js`, vanilla JS,
no framework, no build step) that renders a split-flap "Bahnhoftafel" showing live
departures/arrivals for any of 68 train stations in Kanton St. Gallen, sourced live
from the `transport.opendata.ch` API. It is deployed as-is via GitHub Pages — there is
no server, no bundler, no package.json.

## Commands

There is no build/lint/test tooling in this repo. Development loop:

```bash
# Serve locally (required — app.js does https:// fetches that file:// origin blocks in some browsers)
python3 -m http.server 8787
# then open http://localhost:8787/index.html
```

To sanity-check `app.js` after edits: `node -c app.js` (syntax only, no linter configured).

There is no committed test suite. Verification during development has been done ad hoc
with Playwright (launch Chromium, `page.goto` the local server, screenshot / assert on
DOM state) — there's no `tests/` directory or npm script for this, so write throwaway
scripts against `playwright` if you need to verify UI behavior.

## Deployment

GitHub Pages serves directly from the `main` branch root (no Actions workflow — Pages
"legacy" build). Pushing to `main` is the deploy: `git push` → GitHub rebuilds Pages
automatically within roughly a minute. Repo: `HelmutQualtinger/RebsteinBahnhof`, live at
`https://helmutqualtinger.github.io/RebsteinBahnhof/`.

## Architecture

### Data source

All train data comes from `https://transport.opendata.ch/v1/stationboard` (public,
CORS-open, no API key). Two endpoints are used implicitly through one function:
`fetchPage(stationId, mode, datetime)` where `mode` is `'departure'` or `'arrival'`.

**24h horizon via pagination**: the API's `limit` param caps how many rows come back
per request, so `loadBoard()` in `app.js` pages through by re-querying with
`datetime` set to just past the last returned row's timestamp, accumulating until the
result set covers `HORIZON_HOURS` (24) or a page comes back empty. Dedup is done via a
`Set` keyed by `train name + timestamp` because the API's `limit` semantics can return
overlapping rows across pages (it returns all rows sharing the last included timestamp,
which can span the pagination boundary).

**Fahrplan modal**: each stationboard entry's `passList` array holds the *remaining*
stops after the queried station (not stops before it) — this is what the modal
Fahrplan view renders. The API is known to return a phantom first `passList` entry
with `station.name === null` (a duplicate of a later real stop); `openModal()` filters
these out with `.filter(p => p.station && p.station.name)`. Don't assume `passList`
entries always have names.

### Station list (`STATIONS` in `app.js`)

The 68-entry array is not hand-typed — it was generated by (1) harvesting real
`passList` data from several regional hub stationboards, (2) resolving each stop's
WGS84 coordinate via the API's `/locations` endpoint, (3) point-in-polygon testing
against the official Kanton St. Gallen boundary (swisstopo `swissboundaries3d`, fetched
from `api3.geo.admin.ch`, reprojected from EPSG:21781/LV03 to WGS84). This is why
neighboring-canton stations that are geographically close (e.g. Herisau AR) are
correctly excluded. If this list needs to grow or be re-verified, redo that pipeline
rather than adding entries by hand — there's no source script committed, it was a
one-off analysis.

### State & caching

- `currentStation` / `currentMode` are the two axes of app state. `boardCache` is a
  `Map` keyed by `` `${stationId}|${mode}` `` holding `{ entries, fetchedAt }`, giving
  stale-while-revalidate behavior: switching tabs/stations renders cached data
  instantly if present, then silently refetches in the background if older than
  `CACHE_TTL_MS` (25s). A separate `setInterval` refreshes the *current* station/mode
  every `REFRESH_MS` (30s) silently.
- Selected station persists two ways: `localStorage` (`STATION_STORAGE_KEY`) for return
  visits, and a `?station=<id>` URL query param (synced via `history.replaceState`) so
  shared links open directly to the right board. URL param wins over localStorage on
  load.

### SBB Bahnhofsuhr (analog clock)

Built as inline SVG in `index.html` (`#sbbClock`), modeled on Hans Hilfiker's design:
bold trapezoid hour batons + thin minute ticks generated once at runtime by
`buildClockTicks()`, and hour/minute/second hands rotated every second by
`tickClock()` via `setAttribute('transform', 'translate(50,50) rotate(deg)')` directly
on the SVG elements — **not** CSS `transform`/`transform-origin`. Only `#handSecond`
has a CSS `transition` for the snap-motion easing; the browser transitions the SVG
`transform` attribute change directly (supported in current engines without extra
plumbing). If you change hand shapes, coordinates are defined in a local space where
`(0,0)` is the pivot and `-y` points toward 12 o'clock.

### Sharing / Open Graph

Share buttons (WhatsApp/X/Facebook/mail) in the footer build their `href` dynamically
per selected station (`updateShareLinks()`), pointing at the `?station=<id>` URL. The
Open Graph/Twitter Card meta tags in `index.html`'s `<head>`, and `og-image.png`
(1200×630, generated once from a throwaway HTML render, not committed as source), are
**static** — link-preview crawlers (WhatsApp, Facebook, etc.) don't execute JS, so the
preview card is always the generic site branding regardless of which station is in the
URL. Don't assume per-station preview images work without adding server-side rendering.

### Data quirks worth knowing

- The API's `arrival` field is essentially always `null` for through-stations
  regardless of `type=arrival` vs `type=departure` — only `departure` is reliably
  populated. Both tabs render off the same `departure`-or-`arrival` fallback
  (`hhmm(s.departure || s.arrival)`); there's no real distinct "arrival time" data for
  most of these stops, which is why both tabs can look similar.
- Times from the API are ISO strings already in Swiss local time with offset (e.g.
  `2026-08-04T21:41:00+0200`); `hhmm()` just slices `[11:16]` rather than doing
  timezone math — don't "fix" this into a `Date`-based conversion, it would be correct
  but redundant and risks off-by-timezone bugs from the runner's local TZ.
